## 1. Cartographie

PWA de lecture du Coran : SPA statique React 18 + Vite 8, Tailwind 4, Radix, **sans backend ni compte**. Riwayas Hafs et Warsh, UI FR/EN/AR (RTL natif), tajwid, audio (≈ 54 récitateurs, téléchargement hors-ligne vérifié), tafsir, recherche (worker + voix), mémorisation, bibliothèque (favoris, notes, listes), partage de verset, horaires de prière + suivi, duas, pages éditoriales et légales.

| Couche | Constat |
| --- | --- |
| État | `AppContext` (reducer, sélecteurs `shallowEqual`), persisté en localStorage |
| Données locales | IndexedDB `mushafplus` **v4** (`cache`, `notes`, `bookmarks`, `playlists`), Cache Storage (audio, API, polices QCF), chiffrement AES optionnel (PBKDF2 600 000) |
| Services externes | Quran.com (texte principal), AlQuran Cloud (repli + traductions), Aladhan (prières), CDN audio (everyayah, mp3quran, qurancdn, quranicaudio, quranpedia), jsDelivr/verses.quran.foundation (polices QCF), Wikimedia (adhan), raw.githubusercontent (données Warsh) |
| Build | `vite build` + 6 scripts (manifeste du shell, purge CSS, pages SEO, vérif SEO, budgets, headers) ; `build:ci` exécute 6 gates |
| Déploiement | Vercel **et** Netlify (CSP/en-têtes générés depuis `scripts/cspPolicy.mjs`, test de parité) ; canonique `mon-coran.vercel.app` |
| Tests | 526 tests unitaires `node:test`, ≈ 302 tests E2E Playwright (chromium, firefox, webkit, pwa-offline), axe, WCAG |
| Typecheck | **Non applicable** : pas de TypeScript. Équivalent : `npm run lint` |

## 4. Performance — mesures réelles

Méthode : `reader-ab.mjs` (API Quran.com/AlQuran rejouée depuis un enregistrement, lien partagé simulé FIFO, CPU ralenti par CDP), builds Vite simples de `HEAD` (avant) et de l'arbre modifié (après), 3 exécutions, médiane. Chromium, `/surah/2` (286 versets), viewport 390 px.

| Scénario | Avant | Après | Gain |
| --- | --- | --- | --- |
| Lien lent (150 ms, 1,6 Mb/s), CPU ×1 | 5 582 ms | 4 896 ms | −12 % |
| Lien lent, CPU ×4 | 14 425 ms | 10 408 ms | −28 % |
| Lien rapide (80 ms, 8 Mb/s), CPU ×1 | 2 078 ms | 1 916 ms | −8 % |
| Lien rapide, CPU ×4 | 8 915 ms | 8 696 ms | −2 % (dans le bruit : `[5898, 8696, 9095]` contre `[8908, 8915, 10268]`) |

Limites : un seul navigateur (Chromium), pas de Lighthouse ni de mesure sur appareil réel (**NON TESTÉ**) ; les exécutions sur l'API réelle varient de ±5 s et ne prouvent rien. Le CPU reste le goulot à ×4 : parsing de ~4,4 Mo de JSON, normalisation, écriture IndexedDB, style/layout.

Taille (`build:ci`) : entrée initiale 761,0 → 763,7 kB (JS 402,4 → 403,7 ; CSS 358,6 → 360,0 ; gzip 189,7 → 190,3) ; JS agrégé 1413,3 → 1415,2 kB. **Légère hausse** due aux ajouts (transport, gardes, jeton de couleur). Aucune amélioration de poids n'est revendiquée.

Format de cache : stocker la réponse en texte plutôt qu'en objet dans IndexedDB a d'abord semblé donner −46 % (première visite, CPU ×4) ; la même mesure **entrelacée** (A B A B…, 8 exécutions chacune) donne 6,93 s (ancien) contre 7,24 s (nouveau) : le premier résultat venait de l'ordre des mesures. Le changement a été annulé.

Mesures de diagnostic (état de référence, throttlé Slow 4G + CPU ×4) : accueil FCP ≈ 2,8 s, 60 requêtes, 549 Ko transférés ; lecteur : premier verset > 8 s sur l'API réelle.

## 8. Revue produit (analyse, rien n'a été développé)

Base : dépôt, `ROADMAP.md`, `docs/CONCURRENT_BENCHMARK.md` (veille du 2 octobre). Les hypothèses sont marquées.

**Proposition de valeur** : mushaf fiable, deux riwayas, hors-ligne, privé par défaut, sans compte ni publicité. Différenciants vérifiables dans le code : intégrité du texte testée (Warsh/Hafs), tajwid aligné sur la palette Quran.com, audio hors-ligne **vérifié** (MPEG complet), mode protégé par phrase secrète.

**Friction observée** : sur téléphone, la barre du bas se masque en lecture immersive (le menu « Plus » disparaît jusqu'au prochain toucher) ; le titre de l'en-tête de lecteur alterne entre calligraphie, translittération et traduction (animation continue, vérifié dans le DOM) ; le premier chargement d'une longue sourate dépend de ~600 Ko de JSON. **À CONFIRMER** : onboarding (aucun écran de première utilisation observé), rétention (aucun indicateur : pas d'analytique, par choix).

| Horizon | Propositions (classées par rapport valeur/coût) |
| --- | --- |
| **Quick wins** | Décider d'un plafond par chunk lazy plutôt que d'un agrégat (marge actuelle 4,8 kB) ; borner l'espace IndexedDB par octets et non par nombre d'entrées (après mesure du quota) |

**Dépendances à risque** : Quran.com et AlQuran Cloud pour le texte hafs de repli (pas de SLA ; repli local limité), CDN audio tiers (audit récitateurs en place), polices QCF via jsDelivr/verses.quran.foundation. **Coûts potentiels** : bande passante des services tiers non maîtrisée ; double déploiement Vercel + Netlify à maintenir en parité (test existant).
