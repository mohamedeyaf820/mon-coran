# MushafPlus Security and Privacy Notes

Status: production guidance, not a marketing promise.

## Local data model

MushafPlus is a client-side application. Settings and reading position use
`localStorage`; notes and bookmarks use IndexedDB. Quran text/audio caches and
some study/activity counters are also local, but are not secrets and are not
part of the protected-mode encryption scope.

Browser storage is convenient, not a secure vault. Anyone controlling an
unlocked browser profile can inspect, copy or delete it.

## Default device-key mode

Settings, notes and bookmarks are never newly written as plaintext. By default
they use a random 256-bit device key generated by Web Crypto and stored on the
same browser origin. Records use an authenticated `AES-256-CBC + HMAC-SHA-256`
envelope. Plaintext and former unauthenticated formats are migrated when read.

This default prevents casual reading of stored values, but it is not a strong
security boundary: an attacker who can read the browser profile can normally
read both the device key and the ciphertext.

## Optional protected mode

The Privacy settings tab can protect settings, reading position, notes and
bookmarks with a user passphrase.

- PBKDF2-HMAC-SHA-256 is run through Web Crypto with a unique 256-bit salt and
  600,000 iterations.
- Only the salt, work factor, verifier and lock-screen language are persisted.
  The derived encryption key remains in memory for the unlocked page session.
- Reloading the page or selecting **Lock now** removes that session key and
  mounts the lock screen before the application state is initialized.
- Enabling, changing or disabling protection rotates all in-scope records. The
  two IndexedDB stores are replaced in one transaction; if another write fails,
  the app attempts to restore the previous ciphertext and key metadata.
- There is no passphrase reset or recovery flow. Losing the passphrase makes
  protected data unrecoverable. Export a backup before enabling protection.

The 600,000-iteration work factor follows the current OWASP recommendation for
PBKDF2-HMAC-SHA-256. The implementation caps passphrases at 256 characters to
avoid unbounded derivation input.

References: [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
and the [W3C Web Cryptography specification](https://www.w3.org/TR/WebCryptoAPI/#pbkdf2).

## Limits users must understand

- Protected mode reduces exposure of data **at rest**. It cannot protect an
  already unlocked page, a compromised device, a malicious browser extension,
  injected application code, screenshots, keyloggers or memory inspection.
- The local verifier and salt permit offline passphrase guesses. A long,
  unique passphrase remains essential.
- Note/bookmark content is encrypted, but each IndexedDB primary key still
  reveals the referenced surah and ayah so records remain addressable.
- Full JSON backups and targeted notes/bookmarks exports are deliberately
  readable so they can be restored or opened outside the app. They must be
  stored and shared as sensitive files.
- The manual cloud bridge never runs in the background. It requires a fresh
  consent checkbox, then delegates the destination to the browser share sheet;
  importing requires an explicit JSON file selection. No provider token is
  stored by MushafPlus.
- Clearing site/browser data deletes the device key, protection metadata and
  local records. There is no server copy.
- Quran/audio caches, reading streaks, study scores and other non-core local
  activity data are outside the protected-mode scope in this phase.
- This is local encryption, not end-to-end encryption and not account security.

## CSP and deployment headers

`scripts/cspPolicy.mjs` is the CSP source. `scripts/securityHeaders.mjs`
centralizes the full deployable root-header policy. Netlify and Vercel mirror
that policy, and `scripts/check-security-headers.mjs` fails when either provider
drifts.

Adding an external domain must identify the feature, use the narrowest source
possible and avoid broad user-content allowlists. Production scripts do not
allow `unsafe-eval`; frames and objects are denied.

Run after every CSP/header change:

```sh
npm run audit:headers
npm run test:security
```

## SVG and HTML sanitizing

Sanitizers use a strict tag allowlist. HTML retains only safe presentation
attributes. SVG rejects scripts, foreign content, event handlers, style
attributes, executable protocols and non-fragment URL references. Automated
tests include external filters, data URLs, event handlers and nested active
HTML/SVG content.

## Release checklist

- `npm audit --audit-level=moderate`
- `npm run audit:headers`
- `npm run test:security`
- `npm run build:ci`
- `npm run test:e2e`
- Review any diff touching CSP, deployment headers, crypto metadata or external
  media URLs.
